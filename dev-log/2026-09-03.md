# 开发日志 2026-09-03

## 调整：新增待办插入到置顶块下方的最上方（不再追加到列表最下方）

### 需求（用户报告）

新增待办此前总是排在列表**最下方**（`position = max + 1` 追加到尾部）。
用户期望：新增待办出现在**置顶块下方的最上方**，即非置顶区的第一位，
新记的内容抬头可见。

### 背景：展示排序契约（`expanded_view.refresh`）

```
active.sort(key=lambda i: (not i.sticky, i.position if i.position else 0, i.created_at))
```

置顶块在最上（`not sticky` 为 False 排前），其余按 `position` 升序、
`created_at` 决胜。因此"插到非置顶区最上方" = 让新条目拿到**非置顶项中最小的
position**。

两个易错点（决定实现方式）：

1. 只把自己设为 `min(所有 position)` 而不给别人腾位 → 与原最小值撞车时
   `created_at` 决胜反而把新条目**压到非置顶区最下方**（比旧行为更糟）。
2. 若把"非置顶最小值"误算成"全部最小值"（列表里只有置顶项时最小值属于置顶项），
   新条目会与置顶项 position 冲突；且对所有条目无差别 +1 会无谓扰动置顶项的 position。

### 改动（`app/models/todo_store.py` `add_item`）

- 取 `min(非置顶项 position)`（无非置顶项时取 0）作为新条目 position；
- 所有**非置顶**项 position 整体 +1 腾位（保证全表 position 唯一，置顶项不受影响）；
- 旧的 `max + 1` 尾部追加逻辑移除。

`restore_item`（恢复归档）保持原"尾部追加"语义不变——恢复的是历史条目，
与"刚记录的新事顶到眼前"场景不同，用户未要求改动。

### 测试（`tests/test_todo_store.py`）

- 修改 `test_add_and_load`：单条新增 position 断言 `> 0` → `== 0`；
- 新增 3 项：
  - `test_add_item_inserts_below_sticky_block`：置顶项 + 两条旧待办 + 新增 →
    展示序 = `置顶项, 新待办, 第二条, 第一条`（按视图排序键排序后断言）；
  - `test_add_item_keeps_sticky_positions`：新增不改变置顶项 position；
  - `test_add_item_keeps_non_sticky_positions_unique`：新增后全表 position 唯一。
